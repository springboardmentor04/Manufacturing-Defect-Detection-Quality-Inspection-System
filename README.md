# VisionInspect AI

AI-powered manufacturing defect detection and quality inspection platform built with Vanilla HTML/CSS/JavaScript, FastAPI, YOLO, PostgreSQL, SQLAlchemy, JWT and Docker.

## Important model requirement

Put the actual trained YOLO model at `models/best.pt`, or set `MODEL_PATH`. The backend does not create fake predictions. If the model is missing, startup/inspection fails clearly.

## Local setup

### 1. Python environment

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate
pip install -r backend/requirements.txt
```

### 2. PostgreSQL

Create a database named `visioninspect`, then set `DATABASE_URL`.

### 3. Environment

Copy `.env.example` to `.env` and replace the JWT secret and database credentials.

### 4. Start backend

```bash
uvicorn app.main:app --app-dir backend --reload
```

API docs: `http://127.0.0.1:8000/docs`

### 5. Start frontend

Use any static HTTP server from the project root, for example:

```bash
python -m http.server 5500 --directory frontend
```

Open `http://127.0.0.1:5500/login.html`.

Do not use `file://` for camera capture. Browser camera APIs require a secure context such as localhost/HTTPS.

## Docker

Put `models/best.pt` in the project, then:

```bash
docker compose up --build
```

The API runs on port 8000. For a production frontend, serve `frontend/` with a static web server or add a reverse proxy.

## Architecture

Browser -> REST fetch() -> FastAPI -> image validation/quality -> YOLO -> deterministic severity -> decision -> PostgreSQL -> analytics/reports.

## Roles

Product Manager: business analytics, history, reports, quality trends.

Quality Engineer: upload/camera inspection, detection results, history, manual review.

Authorization is enforced by FastAPI, not by the browser.

## Severity

Severity is:

Size 30% + Location 25% + Defect Type 25% + Confidence 20%.

Ranges: 80-100 Critical, 60-79 High, 40-59 Medium, 0-39 Low.

The class/type mapping is configurable in `backend/app/services/severity_service.py`. Only classes actually emitted by the trained YOLO model are displayed as detections.

## Image quality

Resolution, blur, brightness, contrast and readability are checked before inference. Poor quality leads to MANUAL_REVIEW instead of pretending the model is reliable.

## Reports

PDF reports are generated by the backend with ReportLab.

## Testing

```bash
pip install pytest
pytest backend/tests
```

## Production hardening

- Use a strong random JWT secret.
- Restrict `ALLOWED_ORIGINS`.
- Use HTTPS.
- Store secrets in AWS Secrets Manager / Azure Key Vault or equivalent environment injection.
- Put PostgreSQL on a private network.
- Use object storage for images and replace local storage with an S3/Blob implementation behind a storage service.
- Use Alembic migrations for schema changes.
- Put FastAPI behind a load balancer/reverse proxy.
- Add rate limiting and centralized logs before internet exposure.
- Configure backups and retention for PostgreSQL and object storage.

## AWS deployment

Recommended student-friendly path: containerize the application and deploy the backend container on AWS App Runner or ECS/Fargate, use Amazon RDS for PostgreSQL, and S3 for images. Keep the database private where the chosen architecture permits. Inject `DATABASE_URL`, `JWT_SECRET`, `MODEL_PATH` and other configuration at deployment time.

For heavier GPU inference, move the inference workload to a GPU-capable service such as ECS on a GPU instance or a dedicated inference endpoint. Do not change the application contract.

## Azure deployment

Use Azure Container Apps or App Service for the container, Azure Database for PostgreSQL Flexible Server for the database, and Blob Storage for images. Inject secrets through Azure configuration/Key Vault. For GPU inference, use an appropriate GPU-capable Azure compute/service while keeping the FastAPI API contract unchanged.

## Acceptance flow

1. Register Product Manager and Quality Engineer.
2. Login as Quality Engineer.
3. Upload a real MVTec/test image.
4. YOLO produces actual detections.
5. View bounding boxes, class, confidence, severity, decision and recommendation.
6. Record persists in PostgreSQL.
7. History and analytics update.
8. Manual review stores original and final human decisions separately.
9. Download a PDF.
10. Restart and verify history remains.

## Notes

The supplied project specification requires model metrics such as precision, recall, F1 and mAP to come from actual evaluation results. This implementation deliberately does not invent them. Add a model-evaluation JSON/config endpoint once you have the real validation results from the trained weights.
